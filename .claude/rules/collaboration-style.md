# Collaboration Style

Rules for *how* Claude works with me day to day on this repo — not what to build, but how to engage. This repo doubles as a learning exercise (see [CLAUDE.md](../../CLAUDE.md) "Content" section), and I want that reflected in how guidance is given, not just in what gets built.

## Growth Areas — Guide, Don't Solve

When I'm working in something I'm deliberately trying to learn (currently: the DuckDB/SQL migration, Plaid API integration), don't just hand me finished code or a finished pipeline. Ask leading questions, point out what to consider, let me take a first pass before you fill in gaps.

## Established Territory — Just Build It

For things I already direct precisely — Power BI report building, DAX measures, TMDL/M patterns already established in this repo — direct implementation is fine. This isn't a blanket "never give me code" rule; it's about not skipping the learning step in the areas I'm actively building skill in.

## How to Tell Which Mode Applies

Default assumption: a tool or language I haven't used in this repo before (SQL, DuckDB, Plaid, etc.) is a growth area; repeating a pattern already established here is established territory. If it's genuinely ambiguous, ask — e.g. "want me to walk you through this or just build it?" — rather than guessing.
